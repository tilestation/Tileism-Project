## 13 June 2026 — HR Visa Compliance (Home Office sponsor-licence audit)

### Context
The Home Office asked: *"Please also provide evidence of how you monitor the length of their visa(s)."* The existing HR Documents module tracked expiry dates but didn't produce audit-grade evidence. This build closes that gap.

### Backend
**New route** `routes/hr_visa_compliance.py`:
- `GET /api/hr/visa-compliance/report` — JSON: summary stats (`total_sponsored`, `valid`, `watch`, `expiring_soon`, `expired`, `no_expiry_recorded`, `never_reviewed`) + per-employee rows with current visa doc, status classification, last review entry, and full alert-sent history. Includes a fixed `policy_statement` that explains the monitoring system to the Home Office.
- `GET /api/hr/visa-compliance/report.pdf` — **The artefact you attach to your Home Office reply.** Cover page with policy statement, summary table, full sponsored-worker table with colour-coded status cells, and a per-employee detail page for each EXPIRED / EXPIRING_SOON worker showing all alerts already issued + last review. **New service** `services/visa_expiry_alerts.py`:
- Multi-threshold alert ladder: **90 / 60 / 30 / 7 days** before expiry + EXPIRED sentinel.
- Picks the SMALLEST threshold a visa has crossed (so a 25-day-out visa fires the 30-day notice today, then the 7-day notice when time passes — never both at once).
- Idempotency via `db.hr_visa_alerts` keyed on `(document_id, threshold_days)` — re-running the same day doesn't re-send.
- Each alert email logged into `hr_visa_alerts` with timestamp + recipients = **proof** for the Home Office audit.
- Cron loop in `server.py` runs daily at 07:00 UTC.

**Extended** `routes/hr_documents.py`:

### Problem
- User hit `2267 invoices is over the 500 cap — narrow the range` when trying to export 3 months of invoices for their accountant. The 500 cap was a defensive guard but it broke the legitimate quarterly-accountant use-case.

### Fix
- **Two distinct caps** based on the delivery path's real constraint:
  - **Sync download**: stays at **500** (browser/gateway 60s timeout limit). Anything bigger → use Email instead.
  - **Async email**: **3000** invoices. Endpoint validates + counts synchronously, then schedules the heavy PDF-render + Resend dispatch as a **FastAPI BackgroundTask** so the HTTP response returns instantly with `queued: true`.
- **Auto-split by calendar month** when the resulting ZIP would exceed Resend's 40MB attachment cap. The background task probes the full-range ZIP size first; if too big, it tears down and rebuilds one ZIP per month, sending N emails (one per month) — accountant-friendly layout, sidesteps the size limit by design.
- **Sender heads-up email** when something goes wrong in the background (Resend rejection, etc.) so the admin isn't left wondering.
- **Frontend UI**:
  - Count display now exposes both caps; Email button stays enabled all the way up to 3000 invoices.
  - When count is 501-3000: shows `"X invoices — too big to download, use Email ZIP (auto-splits by month)"` in indigo.
  - When count > 600: dialog warns *"Large batch — will be split into one email per month so each attachment stays under Resend's 40MB cap."*
  - Send button reads **"Queue email"** (not "Send email") and the success toast is the human message returned by the backend.

### [Feb 26, 2026 — Forked session] 📻 Radio Studio Phase 2 — Synchronised Live Stream

**User request**: *"Build a live streaming endpoint (Icecast/Shoutcast style or continuous loop) that 4 Bluetooth speakers can tune into simultaneously."* All 4 stores hear the **same** track at the **same** moment — sync within ~1 s of network jitter.

**Sync strategy (wall-clock tape head)**: Instead of "every connection starts at item 0", we treat the playlist as an infinite loop whose current position is `time.time() % total_loop_duration`. Any client connecting at time `t` joins the loop at exactly that offset. Multiple speakers in 4 stores all compute the same wall-clock offset independently → they converge with no shared session state, no coordinator, no WebSockets.

**Two ways to tune in (both end up synced)**:

1. **`GET /api/radio-studio/live`** — continuous `audio/mpeg` stream (Icecast-style). One async generator per connection yields chunks at the track's real byte-rate (`audio_bytes / duration_seconds`) so the audio player consumes in real time. Polished for VLC and any external app. Works perfectly through Cloudflare + Railway in production.

2. **`GET /api/radio-studio/live/now-playing` + `/stream/{type}/{ref_id}`** — proxy-bulletproof client-orchestrated playback. The polling endpoint returns the current track's `audio_url`, `elapsed_seconds`, and `server_time` so any browser can `<audio src=...>; audio.currentTime = elapsed_seconds; play()` and chain to the next item on `ended`. **This path survives every ingress/firewall** including the Kubernetes nginx-ingress in the preview env that buffers `audio/mpeg` chunked responses.

**Public `/radio` tune-in page** (`PublicRadioPage.jsx`): branded dark-gradient screen with big "Now Playing" display, animated progress bar driven by polled `elapsed_seconds`/`duration_seconds`, "Up next" hint, and a fixed-bottom "Tune in" button (disabled until a playlist exists). Designed for an in-store tablet wall display tethered to a Bluetooth speaker. Uses the orchestrated playback path so it works through every ingress.

**Admin Live Stream panel** (top of the Playlist tab in `RadioStudio.jsx`): gradient card with ON-AIR pill, "Now Playing" strip with ad/music icon + voice + bed metadata + animated progress, "Preview here" button (orchestrated playback for instant in-browser preview), "Open in-store screen" button → opens `/radio` in a new tab, and a tune-in URL strip with copy-to-clipboard for VLC users.

**Backend implementation** (`routes/radio_studio.py` — append 350 LOC at end of file):
- `_locate(offset_seconds, durations)` — pure function, returns `(item_idx, seconds_into_item)`. Heart of the sync guarantee. Trivially unit-testable.
- `_build_play_queue()` — async resolver. Two `find` queries (ads + music), skips dangling refs silently.
- `_throttle_item(item, skip_seconds)` — async generator. Yields 4 KB chunks at the track's actual byte-rate via `asyncio.sleep`.

- `_get_silence_mp3()` — lazily generates 1 s of silent 128 kbps MP3 via ffmpeg, cached as module global. Keeps the socket alive when the playlist is empty.
- `GET /api/radio-studio/live` — `StreamingResponse(audio/mpeg)` with `X-Accel-Buffering: no`, `Cache-Control: no-store`, `Connection: keep-alive`. PUBLIC.
- `GET /api/radio-studio/live/now-playing` — cheap JSON. Returns `now.audio_url`, `now.elapsed_seconds`, `next.audio_url`, `playlist.total_seconds`, `server_time`. PUBLIC.

### [Feb 26, 2026 — Forked session] 🎶 Radio Studio: Background Music Bed (Option A)

**User request**: *"Is there a way to add a bit of nice music to the background of ads or voices, to make it a bit more energetic"*. Picked **Option A** (mix once at generation time, store the result as the only MP3 in Mongo — no playback complexity, no Icecast mixer needed).

**Pipeline (FFmpeg, runs inside `generate_ad_audio` AFTER ElevenLabs returns the voice bytes, BEFORE the size-cap check):**
```
[1:a]aloop=loop=-1,volume=<pct/100>,afade=in[bed]
[0:a]asplit=2[v1][vkey]
[bed][vkey]sidechaincompress=threshold=0.03:ratio=20:attack=5:release=250[bedduck]
[v1][bedduck]amix=duration=first:normalize=0[premix]
[premix]afade=out:d=0.6,alimiter=limit=0.97[mix]
```

- Bed is looped (in case it's shorter than the voice), trimmed (in case it's longer)

### Proportional logic
- `ratio = min(1.0, refund.gross_total / invoice.gross_total)`
- `earned_to_reverse = invoice.trade_credit_earned × ratio` (capped at remaining un-reversed)

## 2026-04-29 — 🔁 Trade credit auto-reverses on refund / cancel / delete

User flagged a real economics gap: when an invoice/order that previously affected a trader's credit balance is undone, the credit ledger was NOT being auto-reversed. So a deleted EPOS invoice would leave the trader with credit they never really earned (and worse, redeemed credit that never came back). Fixed end-to-end across **5 trigger points**.

### Triggers wired
1. **EPOS invoice soft-deleted** (Trash) — credit reversed
2. **EPOS invoice restored from Trash** — credit re-applied (un-reversed)
3. **EPOS invoice permanently deleted** — credit reversed (handles direct perm-delete without going through Trash first)
4. **Online order status → `cancelled`** — credit reversed
5. **Online order status `cancelled` → other** — credit re-applied (handles accidentally-cancelled orders that get resurrected)

### Reversal economics
For each invalidation:
- **Credits earned** by trader: subtracted back from balance (e.g. £5 earned → -£5)
- **Credits redeemed** by trader at the till: added back to balance (e.g. £50 redeemed → +£50 refunded)

Idempotent via a `credits_reversed: true` flag stamped on the invoice/order doc — repeated triggers will NOT double-reverse. Restore unsets the flag so a subsequent delete re-runs.

### Backend

## 2026-04-29 — 🐛 BUGFIX: Live Visitors headline showed inflated count (61 ≠ 2)

### Reported

### Root cause (two compounding bugs from earlier today's work)
1. **Orphan `live_visitors` docs**: when a returning visitor's `restorePersistedLocation()` fired on page load (the "cookie-persist precise location" feature added earlier today), my code did `update_one(..., upsert=True)` against `live_visitors`.
